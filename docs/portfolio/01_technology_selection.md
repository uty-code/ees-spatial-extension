# [Portfolio] 01. 기술 스택 선정 이유 및 의사결정 로그 (Decision Log)

본 프로젝트는 대규모 인원의 평가 데이터를 안정적이고 빠르게 처리하기 위해 최신 기술 스택을 도입하였으며, 각 기술 선정에 대한 명확한 비즈니스적 근거와 기술적 트레이드 오프를 고려하여 설계되었습니다.

## 1. Backend Stack

### ☕ Java 21 (LTS) & Spring Boot 4.x
*   **선정 이유**: Java 21의 **가상 스레드(Virtual Threads)**를 도입하여 I/O 블로킹이 빈번한 DB 연산 환경에서 스레드 리소스 효율을 극대화했습니다.
*   **기술적 고민**: 가상 스레드 도입 시 발생할 수 있는 **피닝(Pinning)** 문제를 방지하기 위해, `synchronized` 블록 대신 `ReentrantLock`을 사용하여 스레드 스케줄링의 병목을 차단했습니다.
*   **대안 고려**: 기존 Thread Pool 방식과 비교했으나, 평가 기간에 집중되는 동시 요청을 처리하기에는 가벼운 가상 스레드가 리소스 절감 면에서 우월하다고 판단했습니다.

### 🦅 MyBatis (Persistence)
*   **선정 이유**: 다면 평가 및 점수 합산 로직은 복잡한 통계 쿼리와 집합 연산이 핵심입니다. SQL 실행 계획을 직접 제어하고 최적화하기 위해 MyBatis를 선택했습니다.
*   **대안 고려 (vs JPA/Querydsl)**: JPA는 생산성이 높지만, 대량 매핑 로직에서 발생하는 복잡한 벌크 연산과 특정 DB 힌트(MSSQL의 `updlock` 등)를 적용하기에는 MyBatis가 더 직관적이고 성능 제어가 용이했습니다. 수동 매핑의 비용은 ResultMap 재사용과 공통 쿼리 모듈화로 해결했습니다.

### 📦 Java Records (DTO)
*   **선정 이유**: 데이터 전달 객체의 불변성(Immutability)을 강제하여 다중 스레드 환경에서의 데이터 안전성을 확보했습니다.
*   **해결 과제**: 상용구 코드를 줄임으로써 코드 리뷰 시 핵심 비즈니스 로직에만 집중할 수 있게 하였고, 안정적인 데이터 전송 계층을 구축했습니다.

## 2. Security & Database

### 🔒 Spring Security & Audit System
*   **선정 이유**: 평가 데이터의 민감성을 고려하여 메소드 단위의 세밀한 인가(`@PreAuthorize`)를 적용했습니다.
*   **기술적 차별점**: 단순히 기능 구현에 그치지 않고, `SecurityUtil`과 `BaseEntity`를 연동하여 모든 CUD 작업 시 수정자 정보가 자동으로 기록되는 **공통 감사(Audit) 시스템**을 구축하여 데이터 추적성을 확보했습니다.

### 💾 MSSQL
*   **선정 이유**: 기업용 엔터프라이즈 환경에서의 안정성과 강력한 트랜잭션 격리 수준 제어를 위해 선택했습니다.
*   **핵심 활용**: 다면 평가 점수 동시 입력 시 발생할 수 있는 Race Condition을 방지하기 위해 MSSQL의 행 단위 비관적 락(`with (updlock)`)을 적극 활용하여 데이터 정합성을 100% 보장했습니다.

## 3. Frontend Strategy

### 🍃 Thymeleaf (Server-Side Rendering)
*   **선정 이유**: 관리자용 시스템의 특성상 복잡한 상태 관리가 필요한 SPA(React/Vue)보다, 빠른 개발 속도와 서버 측 보안 제어가 용이한 SSR 방식을 선택했습니다.
*   **대안 고려**: 초기 로딩 속도와 검색 엔진 최적화(SEO)보다는, 백엔드 개발자의 생산성을 극대화하고 서버 리소스 내에서 인증/인가를 원스톱으로 처리할 수 있다는 점에 가중치를 두었습니다.

---

## 💡 의사결정 회고 (Summary of Trade-offs)
기술 선정의 기준은 언제나 **'현재 비즈니스 문제를 가장 효율적으로 해결할 수 있는가'**였습니다. 트렌드를 맹목적으로 따르기보다, 복잡한 쿼리 제어를 위해 MyBatis를, 고성능 처리를 위해 Java 21 가상 스레드를 선택하는 등 **성능과 안정성 사이의 균형**을 맞추는 데 집중했습니다. 이러한 의사결정 과정은 실제 성능 테스트에서 DB 호출 98% 감소라는 결과로 증명되었습니다.
