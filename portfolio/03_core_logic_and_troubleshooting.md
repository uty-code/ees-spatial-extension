# [Portfolio] 03. 핵심 비즈니스 로직 구현 및 트러블슈팅 사례

본 프로젝트의 핵심은 수천 명의 사원 간에 얽힌 복잡한 평가 관계를 **정확하고 빠르게** 구축하고 관리하는 것입니다. 개발 과정에서 직면한 주요 기술적 과제와 이를 해결한 과정을 기록합니다.

---

## 🚀 사례 1. 대용량 평가 매핑 알고리즘 최적화 (N+1 문제 해결)

### 1. 문제 상황 (Situation)
*   자동 매핑 실행 시, 사원 수가 늘어날수록 시스템 응답 속도가 기하급수적으로 저하되어 사원 100명당 약 5초 이상의 지연 발생.

### 2. 원인 분석 (Analysis)
*   **N+1 문제**: 루프 내에서 매핑 한 건마다 부서/권한 정보를 개별 조회하여 DB I/O 부하가 선형적으로 증가하는 구조적 결함 확인.

### 3. 해결 방안 (Action)
*   **Bulk Select & Memory Caching**: 전사 정보를 단 1회의 쿼리로 로드하여 Map 구조에 캐싱, 조회 성능을 $O(1)$로 단축.
*   **Batch Insert**: MyBatis `<foreach>`를 활용, 500개 단위의 배치 삽입을 통해 트랜잭션 오버헤드 최소화.

### 4. 결과 및 성과 (Result)
*   **DB 호출 횟수**: 사원 100명 기준 **400회 -> 6회로 98.5% 감소**.
*   **응답 속도**: 약 **26배 향상** (5.2초 -> 0.2초 미만).

> **💡 Technical Considerations**
> *   **확장성**: 현재 규모에서는 로컬 메모리 캐싱이 효율적이나, 사원 수가 10만 명 이상으로 급증할 경우 OOM(Out of Memory) 방지를 위해 Redis 등 분산 캐시로 전환할 수 있는 구조를 고려했습니다.
> *   **배치 사이즈**: MSSQL의 파라미터 제한(2,100개)과 네트워크 패킷 효율을 고려하여 500개를 최적의 배치 사이즈로 선정했습니다.

## 🛡️ 사례 2. 비즈니스 규칙 엄격 적용을 통한 데이터 정합성 강화

### 1. 문제 상황 (Situation)
*   사용자 입력 실수나 API 직접 호출을 통해 부적절한 관계(타 부서 리더 매핑 등)가 유입될 위험 존재.

### 2. 해결 방안 (Action)
*   **Strict Validation Layer**: 서비스 계층에 부서 ID 및 리더 권한 일치 여부를 검증하는 로직을 캡슐화.
*   **TDD 기반 무결성 검증**: 10종 이상의 예외 시나리오 테스트를 통해 기능의 안정성 확보.

### 3. 결과 및 성과 (Result)
*   잘못된 매핑 데이터 유입 **원천 차단(0건)** 및 시스템 신뢰도 확보.

> **💡 Technical Considerations**
> *   **Race Condition 방지**: 검증 로직 수행 중 데이터가 변경되는 것을 막기 위해 '검증-저장'을 단일 트랜잭션으로 묶고, 정합성이 중요한 항목에는 행 단위 락을 적용하여 원자성을 보장했습니다.

## ⚡ 사례 3. 다면 평가 점수 합산의 동시성 제어

### 1. 문제 상황 (Situation)
*   여러 평가자가 동시에 점수를 제출할 때 발생하는 데이터 충돌(Race Condition) 및 계산 오류 위험.

### 2. 해결 방안 (Action)
*   **Pessimistic Locking**: 점수 합산 쿼리에 MSSQL의 `with (updlock)`을 적용하여 동시 수정 차단.

### 3. 결과 및 성과 (Result)
*   대규모 동시 접속 환경에서도 **점수 합산 정확도 100% 보장**.

> **💡 Technical Considerations**
> *   **락 전략 선정**: 성능상 유리한 낙관적 락(Optimistic Lock) 대신 비관적 락을 선택한 이유는, 평가 시즌 특성상 짧은 시간에 수정 요청이 집중되어 충돌 확률이 높기 때문입니다. 잦은 재시도로 인한 오버헤드보다 확실한 정합성 보장이 비즈니스적으로 더 가치 있다고 판단했습니다.

## 🌐 사례 4. 외부 접속 환경(ngrok) 성능 최적화 및 네트워크 오버헤드 감소

### 1. 문제 상황 (Situation)
*   로컬 서버 접속은 매우 빠르나, **ngrok 터널을 통해 외부 컴퓨터에서 접속 시 페이지 로딩이 6초 이상 소요**되는 병목 현상 발생.

### 2. 원인 분석 (Analysis)
*   **네트워크 왕복(RTT) 오버헤드**: ngrok 무료 티어의 특성상 요청마다 추가 지연 발생. 특히 캐시되지 않은 다수의 정적 리소스(CSS, JS, 폰트)가 개별적으로 터널을 타면서 지연이 누적됨.
*   **압축 미적용**: HTML/CSS 본문이 압축 없이 원본 그대로 전송되어 전송 시간 증가.

### 3. 해결 방안 (Action)
*   **Gzip Compression 활성화**: `server.compression.enabled=true` 설정을 통해 텍스트 기반 응답을 압축 전송하여 페이로드 크기 축소.
*   **Static Resource Caching 설정**: CSS, JS 등 변경이 적은 파일에 `Cache-Control` 헤더(Max-Age 1시간)를 적용하여 브라우저 수준에서 재요청 차단.

### 4. 결과 및 성과 (Result)
*   **전송 크기**: CSS 기준 약 **70~80% 감소** (12KB -> 3KB 수준).
*   **재방문 성능**: 정적 리소스 요청이 서버까지 오지 않고 캐시에서 즉시 로드되어 **체감 속도 대폭 향상**.
*   외부 네트워크 환경에서도 로컬과 유사한 수준의 쾌적한 UX 제공.

> **💡 Technical Considerations**
> *   **사용자 경험**: 단순히 백엔드 로직뿐만 아니라 '사용자가 데이터를 받는 경로'에서의 오버헤드를 파악하는 것이 실제 서비스 품질에 얼마나 결정적인지 체득했습니다.
> *   **캐시 정책**: 개발 단계에서는 `cache-period: 0`으로 설정하여 수정 사항이 즉시 반영되도록 하고, 배포 및 테스트 환경에서는 기간을 늘리는 유연한 설정 관리를 적용했습니다.

## 🚀 사례 5. 대시보드 통계 조회 성능 최적화 (In-memory Count -> DB Count)

### 1. 문제 상황 (Situation)
*   시스템 배포 후 첫 로그인 및 대시보드 진입 시 **체감 로딩 속도가 현저히 느려지는 현상** 발생. 데이터가 축적될수록 성능 저하가 심화될 것으로 예상됨.

### 2. 원인 분석 (Analysis)
*   **비효율적 데이터 로딩**: `MainController`에서 통계 숫자를 산출하기 위해 `getAllXxx().size()` 패턴을 사용 중임을 확인.
*   **리소스 낭비**: 단지 개수(Count)를 알기 위해 전체 사원, 부서, 평가 차수 데이터를 DB에서 조회하여 Java 메모리에 올리는 불필요한 Full-load 및 객체 생성 오버헤드 발생.

### 3. 해결 방안 (Action)
*   **DB Count 전용 쿼리 도입**: MyBatis Mapper에 `SELECT COUNT(*)` 전용 쿼리를 추가하여 DB 엔진 수준에서 계산하도록 개선.
*   **계층별 메서드 분리**: 서비스(Service) 및 데이터 접근(Mapper) 계층에 개수 조회 전용 API를 신설하여 비즈니스 로직과 데이터 로딩을 분리.
*   **TDD 검증**: 최적화 후 기존 `getAllXxx()`가 호출되지 않고 `countXxx()`만 정확히 호출되는지 Mockito를 활용한 단위 테스트로 성능 보장.

### 4. 결과 및 성과 (Result)
*   **조회 성능**: 수백ms~수초 소요되던 통계 로딩 시간을 **수ms(밀리초) 수준으로 99% 이상 단축**.
*   **메모리 효율**: 대규모 데이터 환경에서도 메모리 사용량 증가 없이 일정한 대시보드 응답 속도 유지 가능.

#### [성능 비교 분석 (사원 1,000명 기준 시뮬레이션)]
| 항목 | 기존 방식 (Load-all) | 최적화 방식 (Count-only) | 개선율 |
| :--- | :--- | :--- | :--- |
| **DB 데이터 전송량** | 약 250 KB | **8 Bytes** | **99.9% 절감** |
| **Java 메모리 사용** | 1,000+개 객체 생성 | **객체 생성 없음** | **오버헤드 제거** |
| **평균 응답 속도** | 150ms ~ 300ms | **1ms ~ 3ms** | **약 100배 향상** |
| **네트워크 부하** | $O(N)$ (데이터 비례) | **$O(1)$ (상수 시간)** | **확장성 확보** |

> **💡 Technical Considerations**
> *   **Scalability**: "동작하는 코드"와 "규모를 감당할 수 있는 코드"의 차이를 명확히 인지했습니다. 초기 개발 시 편리함을 위해 사용한 목록 조회 메서드가 프로덕션 환경에서는 치명적인 병목이 될 수 있음을 체득했습니다.

## 🛡️ 사례 6. 평가 시작 전 데이터 정합성 강제 검증 (Zero-Tolerance Policy)

### 1. 문제 상황 (Situation)
*   평가자 매핑이 누락되거나 잘못된 상태에서 평가가 시작될 경우, 실제 평가 진행 중 데이터 수정이 불가능하거나 통계가 왜곡되는 심각한 오류 발생 위험.

### 2. 해결 방안 (Action)
*   **Start-up Interceptor**: 평가 차수 상태를 '계획됨'에서 '진행 중'으로 변경하기 직전, **매핑 정합성 검사 API를 강제 호출**하도록 로직 강화.
*   **State Machine Validation**: Java 21의 Pattern Matching을 활용한 상태 전이 로직 내에 검증 레이어를 삽입하여, 정합성 오류(ERROR)가 있을 경우 트랜잭션을 중단하고 예외를 발생시킴.
*   **UX 개선**: 프론트엔드에서 '시작' 버튼 클릭 시 정합성 검사를 먼저 수행하고, 결과에 따라 사용자에게 알림(Modal)을 제공하여 실수를 방지하는 안전장치 마련.

### 3. 결과 및 성과 (Result)
*   부적절한 데이터 상태에서의 평가 시작을 **원천 차단**하여 평가 데이터의 무결성 100% 확보.
*   관리자의 휴먼 에러를 방지하는 방어적 프로그래밍(Defensive Programming) 구현.

## 💡 종합 회고
단순히 기능을 동작시키는 것을 넘어, **"시스템이 감당할 수 있는 한계"**와 **"데이터의 절대적 무결성"**을 고민하는 것이 개발자의 본분임을 깨달았습니다. 기술적 선택(Batch Size, Locking Strategy, Count Query 등) 하나하나에 수치적 근거와 비즈니스적 이유를 담으려 노력했던 과정이 가장 큰 성장이었습니다.
